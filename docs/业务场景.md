# 业务场景：银行对公与供应链金融中的单据预审

## 一、痛点

银行在对公业务里要看大量单据：企业客户的费用报销、贸易融资的商业发票、
供应链金融里作为应收账款依据的发票。单据是资金流出的依据，而最省事的造假手法就是**改金额**。

现有两种手段各有缺口：

- **OCR 只识别、不核验。** 读出来的数字格式完好、数量级合理，识别错了看不出来，改过的也看不出来。
- **直接问大模型也不可靠。** 本项目在公开数据上实测：模型被要求核对算术时，会把被改过的数字
  读成"应该是"的原值并判定自洽（CORD 36、92，见 README）。

## 二、与官方查验渠道的分工

中国境内开具的增值税发票与数电票，应当走
[国家税务总局全国增值税发票查验平台](https://inv-veri.chinatax.gov.cn/)。
本工具**不替代**官方查验，覆盖的是它管不到的部分：

| 单据 | 官方查验 | 本工具 |
|---|---|---|
| 境内增值税发票、数电票 | 可查（[查验说明](https://inv-veri.chinatax.gov.cn/fpcysm.html)：限平台开具的发票，每张每天 5 次） | 查验前的字段录入；批量预筛 |
| 境外发票（跨境贸易、港澳报销） | 无中心化渠道 | **主要对象** |
| B2B 商业发票（国际贸易、贸易融资） | 无中心化渠道 | **主要对象** |
| 收据、小票、行程单以外的费用凭证 | 无中心化渠道 | **主要对象** |

## 三、在业务流程中的位置

```
单据上传
  ↓
[转写]      视觉大模型逐格照抄，不做任何计算
  ↓
[核验]      代码侧跑票面自带的各条等式
  ↓
判定        可信 / 存疑 / 无法核验
  ├─ 存疑    → 转人工复核，附上失败的是哪条等式、差多少
  ├─ 无法核验 → 票面缺少核验所需的行，按原流程人工审核
  └─ 可信    → 进入常规抽检
```

**输出可审计。** 每个"存疑"都能指到具体等式，例如：
"第 3 行：112.32 × 1.10 = 123.55，票面含税金额 128.55，差 5.00"。
审核员看的是一条等式，而不是一个黑箱分数。

## 四、为什么这样设计（有数据支撑）

| 设计 | 证据 |
|---|---|
| 模型只转写，算术在代码侧 | CORD validation（预先登记）：本项目 93%，直接问模型 67%（p = 0.039），模型自己核算 78% |
| 多数判定，不偏向"自洽"的读数 | 在两批未参与调规则的数据上合计 7 : 0（p = 0.016） |
| 标注侧与模型侧同一把尺子 | 留出集的两张误报溯源到容差两侧不一致与解析问题，统一后消除 |

## 五、单据类型与伪造成本

单据自带的冗余越多，想把应付金额改掉又不被发现，要同时改的数字就越多：

| 单据 | 票面自带的等式 | 改应付金额而不被发现，至少要同时改 | 状态 |
|---|---|---|---|
| 零售小票（CORD、港式） | 商品行、小计、税费、应付、付款找零之间 4 条 | 商品行、小计、应付，有付款行时再加付款或找零：**3–4 个数** | 已验证 |
| B2B 商业发票 | 行内 2 条 + 合计 4 条（合计印了两遍） | 单价或数量、行金额、行含税金额、Total 行 3 个合计、分税率小计行 3 个数：**9 个数** | 实验中 |
| 中国金融单据（支票、收据、发票） | 另有"大写金额 = 小写金额" | 再多改一处大写，且大写是文字不是数字 | 待做 |

改动一个数字只会破坏 1–3 条等式，但要让所有等式重新闭合，就得把整条依赖链上的数一起改掉。

## 六、边界

- 查的是**票面算术是否自洽**，不是像素取证。把所有相关数字成套改平的伪造检不出来；
  本方法提高的是伪造成本，而不是让伪造不可能。
- 商业发票实验用的是公开的**合成**发票（katanaml-org/invoices-donut-data-v1，MIT），
  版式规整，真实单据的拍照质量、版式多样性会更差。
- 只测了一个视觉模型（DeepSeek）。
